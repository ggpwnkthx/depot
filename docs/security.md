# The headless data backend — Security

The security model of the service and the review of it, item by item.
Every item is answered with a fact: a test, a measurement or a piece
of code.

The rules that the service obeys are in [`SPECS.md`](../SPECS.md) §2.3
(the invariants) and §6.4 (the isolation of the rows). What follows is
the review of those rules and of everything around them.

**The state of the review:** the service is published as `0.1.0`, and it
is a pre-production release: it has never run outside its own harness.
It has no production history, no external user and no audit that was not
written by the author of the code. Every "proved" below means "a check
of this repository passes", and nothing more.

## The model

| The surface | What protects it |
| --- | --- |
| The identity of the caller | A detached JWS of the gateway, verified with `HS256` and a derived key, with the algorithm and the type of the header pinned, and with the payload rebuilt from the request: the transmitted payload is never an input of the decision. |
| The route of the request | The bindings of the deployment, matched on the host and on the path, with an ambiguity refused at load time. The workspace of the path and the workspace of the signature have to be the same one. |
| The capabilities of the caller | The access context of Hub, validated, fresh for every mutation and never cached by default. A missing, an expired or a malformed context is a refusal. |
| The rows | The row level security of PostgreSQL, with the scope set on the transaction: a pooled connection never carries the scope of another request. |
| The fields | The projection of a read is built by the statement: a value the caller may not see never leaves the database. |
| The writes | One complete policy authorizes a write, and the row is checked before the change and after it. |
| The statements | Every value is bound and every identifier comes from the manifest, which is validated as a whole. |
| The history | The audit is append only for the role of the api, and it holds the names of the fields and never their values. |
| The image | A user that is not `root`, no shell, no tool of the build, a base image pinned by digest. |

## The review

| # | What was reviewed | Result | Where |
| --- | --- | --- | --- |
| 1 | **The verification of the identity.** The signature is a detached JWS: the payload is rebuilt from the method, the path, the query, the host and the identity of the headers, and the signature is checked against the rebuilt payload. The algorithm and the type of the header are pinned, the payload segment of the header is never read, and the key is the derived key of the gateway, never the secret of the session. | No finding | `src/domains/gateway-context/verify.ts` |
| 2 | **The fuzzing of the verification.** A random signature, a signature with one of its characters changed, a header of another algorithm or of another type and a truncated signature are all refused, and the verification never throws. The check is in the continuous integration. | Fixed | `test/unit/fuzz.test.ts` |
| 3 | **The route of the request.** The host is compared exactly, the pattern has to match exactly one binding, and a path that carries an encoded separator, a backslash or a dot is not a workspace. | No finding | `src/domains/gateway-context/bindings.ts` |
| 4 | **The workspace of the request.** The workspace of the path and the workspace of the signature have to be the same one: a header that names another workspace is refused. | No finding | `src/domains/gateway-context/index.ts` |
| 5 | **The context of the hub.** The context is validated before it is used, its deadline is checked again immediately before the commit, and the cache of the context is off by default: the revocation of a grant is visible in the next request. A hub that does not answer is a `503`, never a permission. | No finding | `src/domains/authorization/access-context.ts`, `src/domains/authorization/adapters/hub-access-context.ts` |
| 6 | **The isolation of the rows.** The business tables have the row level security of PostgreSQL and it is forced, so the owner of a table is subject to it. The scope is set with `set_config(…, true)`: it is local to the transaction, and a statement that forgets the scope is refused by the database itself. The role of the api may not alter the schema, may not update the audit and may not read the deliveries. | No finding | `migrations/0004_isolation.sql`, `src/platform/postgres/scoped.ts` |
| 7 | **The registry of the workspaces.** The workspace is read before the context of the principal exists, with a reader that may select three columns of one table and may only look a workspace up by its exact identifier. | No finding | `src/platform/postgres/adapters.ts` |
| 8 | **The projection of a read.** The payload of a row is assembled by the statement: a field is added only when a policy that matched the row grants it, so a value the caller may not see never leaves the database. | No finding | `src/domains/records/service.ts` |
| 9 | **The two evaluations of a predicate.** The reads compile a predicate into SQL and the writes evaluate the same predicate in memory, over the row that is locked. The two answers have to be the same, and they were not: the evaluation in memory compared every value with one rule, so a text that looks like a number was compared as a number and the characters were compared with the units of the UTF-16. The comparison is now the comparison of the type of the field, and the predicates of the check are generated instead of written. | Fixed | `src/domains/authorization/filter.ts`, `test/integration/filter.property.test.ts` |
| 10 | **The injection of SQL.** Every value is bound and every identifier comes from the manifest, whose names are validated by a pattern. The fuzzing writes a random filter and a random json and checks that no value of the caller reaches a statement as text and that no identifier of a caller reaches it at all. | Fixed | `src/domains/authorization/filter.ts`, `test/unit/fuzz.test.ts` |
| 11 | **The write of a json field.** A json value that holds a list was bound as the literal of a list of the database, and the statement was refused by the server. The json values are bound as their text. | Fixed | `src/domains/authorization/filter.ts` |
| 12 | **The authorization of a write.** A write is authorized by one complete policy: the predicates and the fields of two policies are never mixed, and a write that no single policy allows stays refused. The update checks the row before the change and the row after it. | No finding | `src/domains/authorization/rules.ts` |
| 13 | **The relation of a write.** A reference has to be readable by the caller in the same tenant and the same workspace, and a reference that is not readable is refused with a generic error: the answer never says whether the target exists elsewhere. | No finding | `src/domains/records/service.ts` |
| 14 | **The concurrency of a write.** A write needs the validator of the record, and two writes with the same validator answer one success and one refusal. The creation needs an idempotency key, and the replay of a key answers the receipt of the first one. The claim of a key waits for the transaction that holds it and is bounded by a lock timeout. | No finding | `src/domains/records/service.ts`, `src/domains/records/canonical.ts` |
| 15 | **The cursor of a page.** The cursor is signed, and it binds the principal, the tenant, the workspace, the collection, the route, the query, the version of the schema, the version of the bundle of the policies and the permissions of the caller. A cursor of one caller is refused by another, a cursor of one query is refused by another, and a cursor of a caller whose permissions changed is refused. | No finding | `src/domains/records/canonical.ts` |
| 16 | **The atomicity of a mutation.** The record, the audit entry, the event and the receipt commit in one transaction, and the check injects a failure at every stage of it. | No finding | `src/domains/records/service.ts`, `test/integration/transactions.test.ts` |
| 17 | **The audit.** The role of the api may insert and read the audit and may not update it. The log holds the identifiers of a mutation and the names of the fields that changed, never their values. | No finding | `migrations/0002_platform.sql`, `migrations/0004_isolation.sql` |
| 18 | **The authority of the worker.** The worker has its own principal and its own route, it asks the hub for a fresh context of its own, and the headers of the user that started the work are never credentials. The depth of the chain of the events is bounded. | No finding | `src/runtime/worker.ts` |
| 19 | **The delivery of the events.** The delivery is at least once, the lease recovers, and a subscriber is registered by the code of the deployment and never by a caller. | No finding | `src/runtime/subscribers.ts`, `src/platform/postgres/adapters.ts` |
| 20 | **The catalog of a workspace.** A registration never creates a table and never names one that the deployment does not declare for it. The publication of a bundle is an operator command and never a route, so the service never holds an authority that bypasses Hub. | No finding | `src/domains/catalog/index.ts`, `scripts/policy.ts` |
| 21 | **The bounds of the work.** The body, the number of the requests in flight, the size of an answer, the depth and the leaves of a filter, the size of a page, the number of the groups and the deadline of a statement are all bounded, and the deadline of the authorization is checked before the commit. | No finding | `src/runtime/config.ts`, `src/domains/records/types.ts` |
| 22 | **The secrets.** The key of the identity is derived from the secret of the session of the gateway, so a backend that is compromised does not compromise the sessions. The secrets are read from files, they are never in the image and they are never in the log: the logger redacts the fields that are known to carry one. | No finding | `src/observability/logger.ts`, `docs/operations.md` |
| 23 | **The metrics.** The endpoint of the metrics answers nothing without its token, and it answers `404` when the deployment has no token. | No finding | `src/app/app.ts` |
| 24 | **The image.** It runs as a user that is not `root`, it has no shell and it carries no tool of the build. The base image is pinned by digest, and the image of the continuous integration is built and started. | No finding | `Dockerfile`, `.github/workflows/ci.yml` |
| 25 | **The dependencies.** The audit of the dependencies is a step of the continuous integration: it fails the build when a dependency carries a known vulnerability. | Fixed | `.github/workflows/ci.yml` |
| 26 | **The comparison of the token of the metrics.** The token was compared with `!==`, so the time of the answer depended on the length of the common prefix of the secret. The two values are hashed before they are compared, and the length of the secret never leaks. | Fixed | `src/app/secrets.ts` |

## The findings that are open

| # | Finding | Severity | Plan |
| --- | --- | --- | --- |
| 1 | **The predicate is evaluated twice.** The reads compile a predicate into SQL and the writes evaluate the same predicate in memory, over the row that is locked. The two implementations are one rule that lives in two places, and they diverged three times before the comparison was made the comparison of the type of the field. The check that keeps them together is a generated one: it writes the predicates that were not written by hand and compares the two answers. | Medium | The two evaluations are the reason the write path holds the row and checks it twice: the row after the change does not exist yet. The structural fix is to give the row after the change to the database as well — a CTE of bound parameters that the same compiler turns into the same predicate — and to keep the evaluation in memory as the oracle of the check. It is a change of the write path of version 0.2, not of the contract. |
| 2 | **The availability of the service is the availability of Hub.** The context of the hub is asked for on every request, because the default of the cache is zero: the revocation of a grant is visible in the next request, and a hub that is down answers `503` to every call of the platform. | Medium | The cache is configurable and its bound is the earlier of the validity that the hub announced and the local lifetime. A deployment that prefers the availability over the instant revocation sets `DATA_CONTEXT_CACHE_TTL_MS`. The bound of the revocation is then the lifetime of the cache plus the duration of the request that is running, and it has to be declared by the deployment. |
| 3 | **The resolution of a timestamp is the millisecond in the write path.** The driver of the database reads a timestamp with the resolution of a millisecond, while the statement compares with the resolution of a microsecond. A row whose timestamp holds a fraction of a millisecond is therefore compared at the millisecond by the write path and at the microsecond by the read path. The api writes the timestamps that the service normalizes to the millisecond, so the rows of the service never hold one: the finding is about a row that was written directly in the database. | Low | The same finding holds for a json field that holds the json `null`: the driver reads it as a null and the statement does not. Both are outside the contract of the service, and the contract says that the tables are written through the api. A row that was written outside of it is a deployment that has broken the contract of the migration. |
| 4 | **The service has never run outside its own harness.** There is no production history, no external user, and no review that was not written by the author of the code. The trace of the implementation maps every requirement of the specification to a check of this repository, and a check of the author of the code is not an assurance. | Medium | The service is published as `0.1.0` and it says so: the release notes and the README mark it as a pre-production release, and the `IMPLEMENTATION.md` says "checked" and not "proved". The first deployment with a real studio and a real tenant is the review that the harness cannot replace. |
