# The security of the headless data backend

The security model of the service and the review of it, item by item.
Every item is answered with a fact: a test, a measurement or a piece
of code.

The rules that the service obeys are in the
[specification](specification.md) §2.3 (the invariants) and §6.4 (the
isolation of the rows). What follows is the review of those rules and
of everything around them.

**The state of the review:** the service is published as `0.3.0`, and it
is a pre-production release: it has never run outside its own harness.
It has no production history, no external user, and no audit that was
not written by the author of the code. Every "proved" below means "a
check of this repository passes", and nothing more.

The next version is `1.0.0`, and it is a release candidate: the gates
of the repository are green, and the two gates that are outside the
repository — a deployment with a real studio and a real tenant, and a
review that was written by somebody other than the author of the code
— are listed in [the readiness of the version 1.0.0](release-readiness.md).
The findings that are open below are the ones that the version `1.0.0`
does not close, and they are open on purpose: they are written down
with their plan.

## The model

| The surface | What protects it |
| --- | --- |
| The identity of the caller | A detached JWS of the gateway, verified with `ES256` and the **public** key of the gateway, with the version, the algorithm and the type of the header pinned by the binding of the route, and with the payload rebuilt from the request: the transmitted payload is never an input of the decision. A backend that verifies an identity cannot mint one. The legacy symmetric format is refused by default. |
| The route of the request | The bindings of the deployment, matched on the host and on the path, with an ambiguity refused at the load time. The workspace of the path and the workspace of the signature have to be the same one. |
| The capabilities of the caller | The access context of Hub, validated, fresh for every mutation, and never cached by default. A missing, an expired or a malformed context is a refusal. |
| The rows | The row level security of PostgreSQL, with the scope set on the transaction: a pooled connection never carries the scope of another request. |
| The fields | The projection of a read is built by the statement: a value the caller may not see never leaves the database. |
| The writes | One complete policy authorizes a write, and the row is checked before the change and after it. |
| The statements | Every value is bound and every identifier comes from the manifest, which is validated as a whole. |
| The history | The audit is append only for the role of the api, and it holds the names of the fields and never their values. |
| The image | A user that is not `root`, no shell, no tool of the build, a base image pinned by digest. |

## The review

| # | What was reviewed | Result | Where |
| --- | --- | --- | --- |
| 1 | **The verification of the identity.** The signature is a detached JWS: the payload is rebuilt from the method, the path, the query, the host and the identity of the headers, and the signature is checked against the rebuilt payload. The version of the signature, the algorithm and the type of the header are the ones of the binding of the route, the payload segment of the header has to be empty, and the key is the public key of the gateway, never the secret of the session and never the private key of the gateway. | No finding | `src/domains/gateway-context/verify.ts`, `src/runtime/identity-keys.ts` |
| 2 | **The fuzzing of the verification.** A random signature, a signature with one of its characters changed, a header of another algorithm or of another type, a signature that carries its payload and a truncated signature are all refused, and the verification never throws. The check is in the continuous integration. | Fixed | `test/unit/fuzz.test.ts` |
| 3 | **The version of the signature is chosen by the deployment and not by the caller.** The binding of a route names the version, the algorithm and the file of the key, and the verification uses exactly those: a route of the version `v5` refuses the version `v4`, a legacy route refuses a public key as its secret, and there is no fallback after a refused signature. The version, the algorithm and the key are never read from the headers of the request. | No finding | `src/domains/gateway-context/bindings.ts`, `src/domains/gateway-context/index.ts` |
| 3b | **The legacy format of the identity.** The symmetric format `v4` is a signing capable secret of the gateway, and a deployment that holds it holds the power to mint an identity. The service refuses it by default: the deployment that still needs it declares it with `DATA_LEGACY_IDENTITY`, and the format is removed in the version `2.0.0`. | Fixed | `src/domains/gateway-context/bindings.ts`, `src/runtime/config.ts` |
| 4 | **The route of the request.** The host is compared exactly, the pattern has to match exactly one binding, and a path that carries an encoded separator, a backslash or a dot is not a workspace. | No finding | `src/domains/gateway-context/bindings.ts` |
| 5 | **The workspace of the request.** The workspace of the path and the workspace of the signature have to be the same one: a header that names another workspace is refused. | No finding | `src/domains/gateway-context/index.ts` |
| 6 | **The context of Hub.** The context is validated before it is used, its deadline is checked again immediately before the commit, and the cache of the context is off by default: the revocation of a grant is visible in the next request. A Hub that does not answer is a `503`, never a permission. | No finding | `src/domains/authorization/access-context.ts`, `src/domains/authorization/adapters/hub-access-context.ts` |
| 7 | **The isolation of the rows.** The business tables have the row level security of PostgreSQL and it is forced, so the owner of a table is subject to it. The scope is set with `set_config(…, true)`: it is local to the transaction, and a statement that forgets the scope is refused by the database itself. The role of the api may not alter the schema, may not update the audit and may not read the deliveries. | No finding | `migrations/0004_isolation.sql`, `src/platform/postgres/scoped.ts` |
| 8 | **The registry of the workspaces.** The workspace is read before the context of the principal exists, with a reader that may select three columns of one table and may only look a workspace up by its exact identifier. | No finding | `src/platform/postgres/adapters.ts` |
| 9 | **The projection of a read.** The payload of a row is assembled by the statement: a field is added only when a policy that matched the row grants it, so a value the caller may not see never leaves the database. The write path builds the same projection: the statement that locks the row computes the flags of the read policies, and the validator of a record is the same whether it was read or written. | No finding | `src/domains/records/service.ts` |
| 10 | **The two evaluations of a predicate.** The reads compile a predicate into SQL and the writes evaluate the same predicate in memory, over the row that is locked. The two answers have to be the same, and they were not: the evaluation in memory compared every value with one rule, so a text that looks like a number was compared as a number and the characters were compared with the units of the UTF-16. The comparison is now the comparison of the type of the field, and the predicates of the check are generated instead of written. | Fixed | `src/domains/authorization/filter.ts`, `test/integration/filter.property.test.ts` |
| 10b | **The predicate of a write is evaluated by the database.** The statement of the write carries the predicates of the policies, compiled by the same compiler as the queries, and the row after the change is given to the database as a common table expression of bound parameters. The evaluation in memory stays as the oracle of the check, and the generated check compares the two answers on predicates that were not written by hand. | Fixed | `src/domains/records/write-guard.ts`, `test/integration/write-guard.test.ts` |
| 10c | **The predicate of a read is evaluated by the database.** The statement that locks the row of a write computes the flags of the read policies, and the representation of the record is built from those flags: the service does not evaluate a predicate of a policy in memory any more. The evaluation in memory of the write path stays as the oracle of the check, and the database decides. | Fixed | `src/domains/records/service.ts` |
| 11 | **The injection of SQL.** Every value is bound and every identifier comes from the manifest, whose names are validated by a pattern. The fuzzing writes a random filter and a random json and checks that no value of the caller reaches a statement as text and that no identifier of a caller reaches it at all. | Fixed | `src/domains/authorization/filter.ts`, `test/unit/fuzz.test.ts` |
| 12 | **The write of a json field.** A json value that holds a list was bound as the literal of a list of the database, and the statement was refused by the server. The json values are bound as their text. | Fixed | `src/domains/authorization/filter.ts` |
| 13 | **The authorization of a write.** A write is authorized by one complete policy: the predicates and the fields of two policies are never mixed, and a write that no single policy allows stays refused. The update checks the row before the change and the row after it. | No finding | `src/domains/authorization/rules.ts` |
| 14 | **The relation of a write.** A reference has to be readable by the caller in the same tenant and in the same workspace, and a reference that is not readable is refused with a generic error: the answer never says whether the target exists elsewhere. | No finding | `src/domains/records/service.ts` |
| 15 | **The concurrency of a write.** A write needs the validator of the record, and two writes with the same validator answer one success and one refusal. The creation needs an idempotency key, and the replay of a key answers the receipt of the first one. The claim of a key waits for the transaction that holds it and is bounded by a lock timeout. | No finding | `src/domains/records/service.ts`, `src/domains/records/canonical.ts` |
| 16 | **The cursor of a page.** The cursor is signed, and it binds the principal, the tenant, the workspace, the collection, the route, the query, the version of the schema, the version of the bundle of the policies and the permissions of the caller. A cursor of one caller is refused by another, a cursor of one query is refused by another, and a cursor of a caller whose permissions changed is refused. | No finding | `src/domains/records/canonical.ts` |
| 17 | **The atomicity of a mutation.** The record, the audit entry, the event and the receipt commit in one transaction, and the check injects a failure at every stage of it. | No finding | `src/domains/records/service.ts`, `test/integration/transactions.test.ts` |
| 18 | **The audit.** The role of the api may insert and read the audit and may not update it. The log holds the identifiers of a mutation and the names of the fields that changed, never their values. | No finding | `migrations/0002_platform.sql`, `migrations/0004_isolation.sql` |
| 19 | **The authority of the worker.** The worker has its own principal and its own route, it asks Hub for a fresh context of its own, and the headers of the user that started the work are never credentials. The depth of the chain of the events is bounded. | No finding | `src/runtime/worker.ts` |
| 20 | **The delivery of the events.** The delivery is at least once, the lease recovers, and a subscriber is registered by the code of the deployment and never by a caller. | No finding | `src/runtime/subscribers.ts`, `src/platform/postgres/adapters.ts` |
| 21 | **The catalog of a workspace.** A registration never creates a table and never names one that the deployment does not declare for it. The publication of a bundle is an operator command and never a route, so the service never holds an authority that bypasses Hub. | No finding | `src/domains/catalog/index.ts`, `scripts/policy.ts` |
| 22 | **The bounds of the work.** The body, the number of the requests in flight, the size of an answer, the depth and the leaves of a filter, the size of a page, the number of the groups and the deadline of a statement are all bounded, and the deadline of the authorization is checked before the commit. | No finding | `src/runtime/config.ts`, `src/domains/records/types.ts` |
| 23 | **The secrets.** The key of the identity is the public key of the gateway: a backend that is compromised cannot sign an identity, and it never holds the private key of the gateway nor the secret of its sessions. The legacy format, which derives the key of the identity from the secret of the session of the gateway, is refused by default and it is removed in the version `2.0.0`. The secrets are read from files, they are never in the image and they are never in the log: the logger redacts the fields that are known to carry one. | No finding | `src/observability/logger.ts`, `src/runtime/identity-keys.ts` |
| 24 | **The metrics.** The endpoint of the metrics answers nothing without its token, and it answers `404` when the deployment has no token. | No finding | `src/app/app.ts` |
| 25 | **The image.** It runs as a user that is not `root`, it has no shell and it carries no tool of the build. The base image is pinned by digest, and the image of the continuous integration is built and started. | No finding | `Dockerfile`, `.github/workflows/ci.yml` |
| 26 | **The dependencies.** The audit of the dependencies is a step of the continuous integration: it fails the build when a dependency carries a known vulnerability. | Fixed | `.github/workflows/ci.yml` |
| 27 | **The comparison of the token of the metrics.** The token was compared with `!==`, so the time of the answer depended on the length of the common prefix of the secret. The two values are hashed before they are compared, and the length of the secret never leaks. | Fixed | `src/app/secrets.ts` |
| 28 | **The failures of the database were internal errors.** A lock that was not granted in time, a constraint that was violated and a statement that ran out of its budget were all answered with a `500 INTERNAL_ERROR`, and the codes that the contract publishes for them were never produced. The translation of the SQLSTATE of the server into the code of the contract is now one table, in the platform layer, and the codes of the contract are the answers of the failures of the database. | Fixed | `src/platform/postgres/errors.ts` |
| 29 | **A refusal of a cursor was an internal error.** The refusal of a cursor was a class of its own and it was never caught: a cursor that was tampered with answered `500 INTERNAL_ERROR` and not the `400 INVALID_CURSOR` of the contract. The refusal is a `ServiceError` now, and the reason of the refusal is the cause of the error and not its message: the answer of the service is the safe summary of the code. | Fixed | `src/domains/records/canonical.ts` |
| 30 | **A statement that failed took the connection of the pool with it.** A statement that failed marked the transaction as broken, and a broken connection was neither returned to the pool nor destroyed: the connection was lost. A client that sent twenty failing writes exhausted the pool of the api, and every request of the deployment answered `503` afterwards. A statement that fails does not break a connection, and a connection that is broken is destroyed and not returned to the pool. | Fixed | `src/platform/postgres/scoped.ts` |
| 31 | **The budget of the size of an answer was checked after the answer was built.** The four mebibytes of the contract were checked once the page and its expansions were in memory, so the budget bounded the bytes that leave the service and not the memory that it holds. The expansion of a relation was read with one statement per root row, and the answer could hold a thousand related rows of two hundred kilobytes before it was refused. The budget is now spent as the answer is built, the expansion is read in chunks whose size follows the size of the rows, and the relation of a page is read with one statement and not with one per row. | Fixed | `src/domains/records/budget.ts`, `src/domains/records/service.ts` |
| 32 | **The cache of the context was not bounded.** The cache was a map without a bound and without a sweep: an entry left the cache only when the same key was asked again. The cache is the mitigation of the availability of Hub, and a mitigation that grows without a bound is a leak. The cache is bounded now, the entries that are spent leave it, and the entry that is the least recently used leaves it when it is full. | Fixed | `src/domains/authorization/index.ts` |
| 33 | **There was no bound of a tenant.** The bound of the listener is the bound of the machine, and a tenant that sent more requests than the others took the room of the others: the answer of the listener was a `503 OVERLOADED`, and it told the caller that the service was broken rather than that it was sending too much. The bound of a tenant is applied once the tenant of the request is known, and it answers a `429 TOO_MANY_REQUESTS` with a `Retry-After`. Its default is the room of the whole process, and a deployment with several tenants declares the room that each of them holds. | Fixed | `src/runtime/limits.ts` |
| 34 | **The suites might have no power.** Every check of this repository was written by the author of the code, and a check that agrees with the code because it shares its assumptions proves nothing. The gate of the mutation breaks the code on purpose — the type of the protected header, the expiry of a cursor, the scope of a cursor, the fields of a row, the predicates of a write, the bound of the cache, the connection of the pool — and it checks that the suites notice. The gate found five behaviours that nothing proved, and the suites that prove them were written. | Fixed | `scripts/mutation.ts` |
| 35 | **The history of the versions holds the values of the records.** The audit holds the identifiers of a mutation and the names of the fields that changed, and it never holds a value: the images of the versions are a separate surface, and they are the first of the service that holds the values of the business. They are read with the policies of the deployment — the database evaluates the predicates of the read policies over the image of every version, exactly as it evaluates them over the record — and a rollback is a write that the same policies authorize. A version that the policies hide is not found, and a rollback that they forbid is refused: the history is not a path that bypasses the authorization. The images are written by the statement of the change, and the role of the api may not update nor delete them: the retention of the history is the work of the maintenance role. | No finding | `migrations/0008_record_versions.sql`, `src/domains/records/service.ts`, `src/domains/records/write-guard.ts` |

## The findings that are open

| # | Finding | Severity | Plan |
| --- | --- | --- | --- |
| 1 | **The predicate is evaluated twice.** The reads compile a predicate into SQL and the writes evaluate the same predicate in memory, over the row that is locked. The two implementations are one rule that lives in two places, and they diverged three times before the comparison was made the comparison of the type of the field. The check that keeps them together is a generated one: it writes the predicates that were not written by hand and compares the two answers. | Medium | **Closed.** The statement of the write carries the predicates of the policies, and the row after the change is given to the database as a common table expression of bound parameters: the check of a write is the check of the row that the write produces. The evaluation in memory stays as the oracle of the check, and the generated check of the guard compares the two answers on predicates that were not written by hand. |
| 2 | **The availability of the service is the availability of Hub.** The context of Hub is asked for on every request, because the default of the cache is zero: the revocation of a grant is visible in the next request, and a Hub that is down answers `503` to every call of the platform. | Medium | The cache is configurable and its bound is the earlier of the validity that Hub announced and the local lifetime. A deployment that prefers the availability over the instant revocation sets `DATA_CONTEXT_CACHE_TTL_MS`. The bound of the revocation is then the lifetime of the cache plus the duration of the request that is running, and it has to be declared by the deployment. **The reference deployment declares it:** the default of no cache, and the bound of the revocation is the duration of the request (see [the capacity](capacity.md)). |
| 3 | **The resolution of a timestamp is the millisecond in the write path.** The driver of the database reads a timestamp with the resolution of a millisecond, while the statement compares with the resolution of a microsecond. A row whose timestamp holds a fraction of a millisecond is therefore compared at the millisecond by the write path and at the microsecond by the read path. The api writes the timestamps that the service normalizes to the millisecond, so the rows of the service never hold one: the finding is about a row that was written directly in the database. | Low | The same finding holds for a json field that holds the json `null`: the driver reads it as a null and the statement does not. Both are outside the contract of the service, and the contract says that the tables are written through the api. A row that was written outside of it is a deployment that has broken the contract of the migration. |
| 4 | **The service has never run outside its own harness.** There is no production history, no external user, and no review that was not written by the author of the code. The suites of the tests map every requirement of the specification to a check of this repository, and a check of the author of the code is not an assurance. | Medium | The service is published as `0.3.0` and it says so: the release notes and the README mark it as a pre-production release, and the suites say "checked" and not "proved". The first deployment with a real studio and a real tenant is the review that the harness cannot replace. **The gate of the mutation is the part of the plan that the repository can hold:** it does not replace the review of somebody else, and it answers the part of the question that a machine can answer — does the suite notice when the code is broken on purpose. It found five behaviours that nothing proved. |
| 5 | **The suites and the code share their assumptions.** A suite that was written by the author of the code agrees with the code when the code is wrong in a way that the author imagines. The gate of the mutation is the answer to that risk, and it is a partial one: it only covers the mutations that were thought of, and a mutation that survives is a behaviour that nothing in the repository proves. | Medium | The gate is a step of the continuous integration, and it grows with the code: every behaviour that the security review names has a mutation that breaks it, and the suite that catches the mutation is named by the mutation. The gate of the repository covers fourteen mutations of the trust boundary; the review of somebody else is still the gate that the repository cannot hold. |
